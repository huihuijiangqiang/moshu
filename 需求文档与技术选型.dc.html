产品定位：面向中文长篇连载的可审阅 AI 写作台。一键成章只是入场能力；每一段 AI 修改可追踪、每一条长程冲突有证据、80 万字仍按固定预算稳定续写，才是核心承诺。

01  用户与场景

三类用户的核心矛盾不同，MVP 只优先满足前两类，第三类的数据结构要提前留好。

P0
全职日更作者

要的是速度，怕的是失控。日更压力下需要 AI 铺量，但绝不接受读者认出「AI 味」，也不接受写到后期人设崩坏。

关键任务
今天要交 3 章 → 从章纲生成初稿 → 按自己的风格改 → 确认无设定冲突 → 发布
P0
新人兼职作者

要的是「能开工」。不会搭框架、不懂黄金三章，需要产品把流程铺好，用模板引导他做出第一个可读的开头。

关键任务
一句灵感 → 选题材模板 → 生成设定与总纲 → 出前三章 → 看到「可以继续」的信号
P1 · 第二阶段
内容工作室

要的是产能可控。多个写手同时写一个 IP，需要共享设定、统一风格、可审稿、可看产量。付费能力最强。

MVP 需预留
组织 / 成员 / 角色权限三张表，作品归属于组织而非个人

02  功能需求

P0 = MVP 必须有；P1 = 第二阶段；P2 = 观察后再定。带 ★ 的是差异化功能，验收标准要写死。

优先级 模块 需求描述 验收标准
P0 项目与章节管理 作品 / 卷 / 章三级结构，拖拽排序，回收站，字数与日更统计。 80 万字作品打开首屏 < 2s；章节切换 < 200ms。
P0 ★ 持续大纲规划 故事总述、卷纲、章名、章纲节点与时间线在创建后持续可编辑；支持插章、节点增删与排序、自动保存和版本号。已有正文的章节修改章纲时，作者必须选择“仅更新计划”或“更新计划并标记正文待调整”，系统不得自动修改正文。 向导生成的骨架创建后不丢失；大纲与写作台读取同一版本；保存冲突不静默覆盖；选择标记后写作台和大纲均显示“正文待调整”，未选择时正文内容与状态保持不变。
P0 写作编辑器 专注写作界面，自动保存，版本历史，离线草稿；选中文本唤起 AI 浮层（续写 / 扩写 / 润色 / 改写）。正文段落具备稳定 id。 80 万字 / 270 章基准项目首屏 < 2s，切章 < 200ms；守卫问题可按段落 id 精确跳转。
P0 可信保存与恢复 本地草稿、服务端自动保存与版本快照三层保护；使用 base_rev 乐观锁，冲突时展示双版本；切章、关闭和失焦前安全 flush。 自动保存间隔 ≤ 3s；断网可继续写，重启后可恢复；模拟断网、快速切章、双端冲突和异常退出均不静默丢字或覆盖。
P0 开书向导 灵感一句话 → 读者方向 → 题材分类与细分题材 → 最多 3 个内容标签 → 故事模板 → AI 生成设定 + 总纲 + 卷纲 → 生成前三章。题材覆盖玄幻仙侠、都市现实、历史军事、悬疑科幻、言情情感、游戏轻小说，并允许自定义；每步可编辑后再进下一步。 新用户从注册到拿到第一章正文 < 5 分钟；题材必须选择到细分类或填写自定义题材，内容标签可不选且最多选 3 个，中途退出后可恢复全部选择并续做。
P0 一键成章 基于章纲 + 设定库 + 前情摘要生成整章正文，流式输出，可中断、可重生成、可只重写某段；生成结果先进入候选草稿。 3000 字章节首字延迟 < 3s，全章 < 90s；重生成保留已锁定段落；失败时保留已生成内容并给出重试动作。
P0 ★ AI 变更审阅与来源 生成、改写和守卫修复统一进入 Change Review；支持逐段接受 / 拒绝、整批处理和一次撤销；记录 human / ai-raw / ai-edited 来源。 未接受内容不计入正文字数、不触发正式保存；所有 AI 改动可定位、可回退，刷新后待审状态不丢失。
P0 设定库 人物 / 势力 / 地点 / 物品 / 力量体系 / 伏笔六类条目，支持关系与别名；正文中 @ 引用并高亮。 条目被引用时生成必然注入；条目改名后正文引用自动跟随。
P0 ★ 一致性守卫 每章采纳后异步检查人物属性、物品状态、时间线、信息知情边界、能力规则、地理距离与伏笔；每条告警展示证据、来源章节、置信度和建议动作。 版本化评测集召回率 ≥ 70%，误报率 ≤ 20%，证据定位准确率 ≥ 90%；用户可忽略、修复或反馈，处理结果用于压低同类误报。
P0 模型与额度 基础档国产模型无限量，高级模型按积分计费；用量面板显示本月消耗。 额度不足有明确提示与降档建议，不静默失败。
P0 导出 全量导出正文（TXT / DOCX / Markdown）+ 设定库 + 大纲 + 开放 JSON 备份，一键打包，无需付费；EPUB 列为 P1。 导出包可在新账号或空项目中完整恢复；格式选择必须产生对应格式，不以 TXT 占位。
P1 ★ 作者风格指纹 上传本人 ≥ 5 万字旧作，抽取风格档（句长分布、对白占比、口头禅、意象偏好、章末钩子），生成时对齐并给偏离度评分。 盲测中作者本人认为「像我写的」比例 ≥ 60%。
P1 AI 占比自查 给出全章 AI 生成占比与「疑似 AI 句式」标注，辅助规避平台审查。 标注可逐句跳转，可一键重写。
P1 拆书 导入他人作品，输出节奏节点、爽点分布、章纲结构，供学习参考。 仅供参考不入库，避免侵权风险提示。
P1 ★ 工作室产线 组织共享设定库与风格档；主笔派章、写手领章、主编审稿留批注；产量看板。按席位计费。 同一作品 5 人并行不冲突；审稿意见可定位到段落。
P2 转剧本 / 短剧 小说转剧本格式、分镜。竞品已有，但非核心用户诉求。 观察工作室客户是否真实需要后再定。
P2 平台直投 对接平台投稿接口。依赖商务，不确定性高。 —

03  核心机制：分层记忆

这是整个产品的技术心脏。每次生成请求的上下文按固定预算装配，长度不随作品字数增长。

第 1 层 · 常驻
稳定设定

主角卡、金手指、力量体系、世界规则、风格档。整本书内极少变化。

预算 ~6k token
策略 全量 + prompt caching
第 2 层 · 检索
相关条目

本章章纲里出现的人物、地点、伏笔条目。走实体索引精确命中，向量检索兜底。

预算 ~5k token
策略 章纲实体抽取 → 索引查询
第 3 层 · 滚动
前情摘要

每章写完生成 200 字摘要；每 10 章压缩成卷级摘要。逐级压缩，长度恒定。

预算 ~4k token
策略 章摘要 + 卷摘要金字塔
第 4 层 · 原文
相邻上下文

前 2 章原文（尤其上一章结尾）。保证文气与场景连续，这层不能省。

预算 ~10k token
策略 定长截取，优先章末
设计约束

单次生成上下文硬上限 25k token。任何功能不得突破——突破了成本模型就崩了，而且长上下文并不会让输出更好，只会更贵更慢。

04  技术选型

前端按你的要求定为 Vue 3。选型原则：编辑器是唯一不能妥协的地方，其余一切从简。

前端
Vue 3.5 + TypeScript + Vite — 组合式 API，<script setup>
Pinia — 状态；作品/章节/设定库各一个 store
Vue Router — 编辑器路由用 keep-alive 保活
UnoCSS 或 Tailwind — 原子化，配合设计 token
TipTap 3（@tiptap/vue-3） — 编辑器核心，见下方说明
VueUse — 自动保存、快捷键、离线检测
Dexie（IndexedDB） — 离线草稿与断网续写
Element Plus — 仅后台/设置页，正文界面不用
编辑器为什么选 TipTap 而不是 wangEditor / Quill：AI 建议的「接受 / 拒绝 / 局部重写」需要在文档模型上叠加临时装饰层（decoration）与自定义节点，这是 ProseMirror 的强项。TipTap 是 headless 的 ProseMirror 封装，官方支持 Vue 3。@tiptap/suggestion 直接用来做 @ 引用设定条目。wangEditor 开箱快但扩展模型弱，做到「AI 段落作为可回退的节点」会很痛。
工程基线：固定 Node 22 或 24 LTS，提交唯一 lockfile；CI 必须依次通过类型检查、单元测试、生产构建和依赖审计。不得把“Vite 可转译”当作“可发布”。
后端
Python + FastAPI（已采用）—— 与算法链路共用 Python 生态，一致性守卫与摘要任务无需跨语言。
PostgreSQL + pgvector — 关系数据与向量检索合并在一处，MVP 阶段不要引入独立向量库。
Redis + Celery / BullMQ — 摘要生成、一致性检查、风格抽取全部异步化，绝不阻塞写作。
SSE 而非 WebSocket — 生成是单向流，SSE 更简单且穿透代理更稳；协作阶段再上 WebSocket。
模型层
自建模型网关：统一 OpenAI 兼容协议，按任务路由（摘要用便宜模型、正文用主力模型、高级档可选顶级模型），失败自动降级，全量记录 token 与成本归因到用户。
必须支持 prompt caching——第 1 层设定常驻，这是成本模型成立的前提。
不做自研模型。MVP 阶段的差异化在上下文工程和产品逻辑，不在模型权重。
协作（P1）
Yjs + Hocuspocus — TipTap 官方协作方案，工作室阶段接入。
提醒：MVP 阶段不要提前引入 Yjs。它会改变整个持久化模型，在单人场景纯属负担。但数据库设计时把章节正文作为独立文档存储，为将来切换留出余地。

05  前端要提前解决的六个硬问题

这些问题直接决定正文是否安全、长篇是否可用，不应推迟到视觉收口阶段。

01
绝不把整本书装进一个文档

80 万字放进单个 ProseMirror 文档会直接卡死。一章一文档，章节列表只加载元数据（标题、字数、状态），正文按需拉取，切章卸载。左侧章节树超过 200 项时用虚拟滚动。

02
流式插入不能打断光标

SSE 逐块到达时，若直接 insertContent 会不断重置选区、污染撤销栈。做法：AI 输出先进独立的草稿节点（自定义 node，带 pending 标记，不进 history），用户点「采纳」时才作为一次事务合并进正文——撤销一次即可全部回退。

03
丢稿是不可原谅的

三层保险：本地 IndexedDB 合并写入（≤ 500ms）、节流 3s 上传服务端、服务端保留最近 50 个版本快照。保存携带 base_rev，切章前等待 flush；恢复时比较本地与服务端版本，冲突并列展示，永不静默覆盖。

04
设定引用要活着

@ 引用存的是条目 id 而非文字（自定义 inline node，渲染时读当前名称）。这样改名自动跟随，且服务端能精确知道本章引用了哪些条目——一致性检查和上下文装配都依赖这份引用关系。

05
窄屏不能把正文挤没

桌面编辑器最低支持宽度 1024px；低于该宽度时左右栏变为互斥抽屉，正文保持可读。移动端 MVP 虽不提供完整编辑，也必须支持只读、搜索与灵感速记，页面不得横向溢出。

06
错误必须可见、可恢复

真实 SSE 先检查 HTTP 状态并区分主动停止、鉴权、额度、冲突和网络失败。失败草稿保留部分内容，进入明确的错误状态，并提供重试、降档或丢弃动作；状态变化通过 aria-live 告知辅助技术。

MVP 发布质量门
构建：类型检查、单测、生产构建全部通过，使用 lockfile 冷安装可复现。
安全：生产依赖无已知 high / critical；开发依赖例外必须记录原因和隔离措施。
浏览器：11 个核心路由无 console error；1440 / 1024 / 390px 均无内容遮挡或页面横向溢出。
数据：真实 API 下通过自动保存、离线恢复、409 冲突、切章 flush 和 SSE 失败集成测试。
性能：270 章基准达到首屏与切章指标；1000 章压力测试不一次加载全部正文。
可访问性：主结构使用语义标题，键盘可完成核心写作流，异步状态可被辅助技术感知。

07  里程碑（10 周 MVP）

第 1-2 周
骨架

固定 Node LTS 与 lockfile，修复类型 / 测试 / 构建，打通真实章节 CRUD、base_rev、冲突处理与启动恢复。

第 3-4 周
设定库 + 网关

稳定段落 id、来源标记、六类设定条目、@ 引用节点；完成窄屏抽屉和编辑器性能基准。

第 5-6 周
生成链路

模型网关、真实 SSE、分层记忆装配、一键成章、统一 Change Review 与章摘要异步生成。

第 7-8 周
一致性守卫

版本化评测集、设定抽取、七类冲突检测、证据定位、处置反馈与伏笔追踪。按召回和误报数据收口。

第 9-10 周
收口

开书向导、可恢复导出、额度与支付；完成发布质量门并以 10 位种子作者的真实长篇项目内测。

明确不做（MVP）
