一个必须先补的前端约定：守卫要能「一键跳到出问题的那一句」，这需要正文里有稳定的段落锚点。TipTap 默认段落无 id，重排后位置就漂了。解法：给 paragraph 加一个 data-pid 属性（nanoid，创建时生成、复制时重生成），守卫结果按 pid + 字符 offset 定位。这件事越晚做越贵——已有正文需要回填迁移。

02  后端技术选型（已决议）

Python + FastAPI。取舍依据：一致性守卫、章摘要、风格抽取三条链路全是算法活，放在 Python 生态省一次跨语言序列化与一次团队协作边界。

运行时
Python 3.12 + FastAPI — 异步原生，SSE 用 StreamingResponse
Uvicorn + Gunicorn — 生产多 worker
Pydantic v2 — 请求/响应模型，与前端 TS 类型对齐
uv — 依赖与虚拟环境管理，比 poetry 快一个量级
SQLAlchemy 2.0（async） — ORM，asyncpg 驱动
Alembic — 迁移，每次改模型必须生成迁移
Celery + Redis — 异步任务；守卫、摘要、风格抽取全走这里
pytest + pytest-asyncio — 测试
存储
PostgreSQL 16 + pgvector — 关系数据与向量检索合一。MVP 不引入独立向量库：条目量级在千级，pgvector 的 HNSW 索引完全够用，而且第 2 层检索主路径是实体索引精确命中，向量只是兜底
Redis 7 — Celery broker + 生成状态缓存 + 额度扣减的原子计数
对象存储（S3 兼容 / MinIO） — 导出包、风格档上传的旧作原文、版本快照的冷数据
正文存哪：章节正文存 PostgreSQL 的 chapter_body 独立表（一行一章，content_html + content_json 双写）。独立表而非 chapters 表的列，原因有三：列表查询永不误带正文、将来切 Yjs 时只换这一张表、版本快照可以只对这张表做。
模型网关
自建薄网关，不用 LiteLLM 之类的全功能框架——我们需要的只有四件事：统一 OpenAI 兼容协议、按任务路由、失败降级、token 归因记账。自己写 300 行比接一个框架再绕过它的抽象更省
必须支持 prompt caching — 第 1 层设定常驻是成本模型成立的前提。网关层要保证同一作品的 system 段字节级稳定，否则缓存命中率归零
任务路由表：摘要与实体抽取走便宜档、正文生成走主力档、高级档可选顶级模型、守卫的冲突判定走中档 + 结构化输出
缓存命中的硬约束：prompt 的前缀必须字节稳定。这意味着第 1 层设定的序列化顺序要固定（按条目 id 排序，不按更新时间），且第 1 层与第 2 层之间要有明确分隔符。设定改动时缓存失效是正常的，但不能因为排序抖动而无谓失效。
传输与部署
SSE 而非 WebSocket — 生成是单向流。注意 Nginx 要关 proxy_buffering，否则首字延迟 < 3s 的验收标准直接失败，这是最常见的坑
Docker Compose（MVP）→ K8s（工作室阶段）。MVP 阶段别上 K8s，运维成本换不来收益
鉴权：手机号/邮箱验证码 → JWT（access 30min + refresh 30d），refresh 存 Redis 可吊销。SSE 的 token 通过 POST body 传，不走 query string——query 会进 Nginx access log

按领域切分而非按技术分层。memory/ 与 guard/ 是产品的两个心脏，各自独立成包，不许业务代码直接调它们的内部函数。

两条目录纪律：其一，api/ 层不允许出现业务逻辑，它只做参数校验与响应组装——这样将来换 GraphQL 或加 gRPC 时业务代码零改动。其二，memory/ 与 guard/ 只暴露包级入口函数，内部实现随时可重写；算法同学在这两个包里迭代不会波及后端同学的进度，这是 6 人团队能真正并行的前提。

04  数据模型

十九张表，分五组。前六张是骨架，codex_* 四张支撑设定库与第 2 层检索，守卫资产两张，风格 / 用量 / 占比四张，最后三张是组织权限——MVP 建表但不开功能。

表 关键字段 要点
骨架
users id, phone, email, plan, credits_remaining, credits_quota, created_at 无密码。credits_* 的写操作必须走 Redis 原子计数再落库，否则并发生成会超扣或漏扣
projects id, owner_id, org_id, title, genre, status, daily_goal, style_profile_id, cover_url org_id 从第一天就建，个人作品填个人默认组织。后补这一列要改所有查询的 where 条件
volumes id, project_id, idx, title, summary summary 是第 3 层的卷级摘要，每 10 章由 Celery 压缩生成
chapters id, project_id, volume_id, idx, title, words, status, outline(jsonb), outline_note, summary, deleted_at 此表永不含正文——这是首屏 < 2s 的唯一保证。idx 用间隔 1024 的稀疏整数，拖拽换序只改一行
chapter_bodies id, chapter_id, content_html, content_json(jsonb), rev, updated_at 一行一章，独立表。content_json 存 ProseMirror doc，守卫与占比分析读它而非 HTML。rev 单调递增，用于离线冲突判定
chapter_versions id, chapter_id, rev, content_html, created_at, trigger 每章保留最近 50 个快照，超出删最旧。trigger 记来源（autosave / accept-draft / manual）
设定库与检索
codex_entries id, project_id, kind, name, summary, attrs(jsonb), resident, status, embedding(vector) attrs 存结构化属性（如「左手：已断，第 12 章」），冲突检测比对的是它而非自由文本。status='pending' 是守卫抽取待确认
codex_aliases id, entry_id, alias 独立表而非数组列——第 2 层的实体索引要对别名建 GIN 索引做精确命中
codex_refs chapter_id, entry_id, occurrences 一致性检查与上下文装配的共同基础。保存正文时从 content_json 扫 CodexRef 节点全量重建本章的行
codex_relations id, from_entry_id, to_entry_id, kind, note 人物关系图。MVP 只做展示与注入，不做图推理
守卫资产
guard_issues id, project_id, kind, severity, category, title, chapter_id, anchor(jsonb), evidence(jsonb), resolution, resolved_at, false_positive anchor 存 {pid, start, end}，前端靠它跳到出问题那一句。false_positive 回流评测集，用于持续调准
foreshadows id, project_id, entry_id, planted_chapter, expected_by_chapter, status, closed_chapter 伏笔独立成表而非塞进 codex——它有生命周期与倒计时，查询模式完全不同
风格、用量、占比
style_profiles id, user_id, name, source, sample_words, is_default, dimensions(jsonb), extracted_at dimensions 存六维抽取结果。归属 user 而非 project——风格档跨作品复用
generation_runs id, user_id, chapter_id, kind, model, prompt_tokens, cached_tokens, completion_tokens, credits, accepted_words, layer_report(jsonb) accepted_words 是北极星指标的数据源，采纳时回写。layer_report 存四层实际 token 占用，用于调预算
usage_logs id, user_id, run_id, feature, credits, created_at 用量面板按 feature 聚合。基础档记 0 积分但仍要记行，成本核算需要
ratio_reports id, chapter_id, ai_raw, ai_edited, human, segments(jsonb), computed_at 占比靠采纳时打标而非事后检测：草稿采纳时段落标 ai-raw，用户编辑后降级 ai-edited
组织权限 · MVP 建表不开功能
orgs id, name, plan, seats, created_at 个人用户注册时自动建一个单人组织，避免两套归属逻辑
org_members org_id, user_id, role, joined_at role 枚举：owner / lead（主笔）/ writer（写手）/ editor（主编）
chapter_assignments id, chapter_id, assignee_id, assigner_id, state, due_at 派章领章。MVP 不用，但建表能让 chapters 查询从一开始就带 assignee 视角
最容易被忽略的一张表

codex_refs 决定第 2 层检索的精确率、守卫的检查范围和「改名自动跟随」的正确性。它必须在每次正文保存时全量重建，不能增量更新——增量会漏删。

05  接口契约

与 app/src/api/mock/index.ts 的方法签名一一对应。前端把 mock 换成 request() 调用即可，视图层零改动。

接口 对应 mock 方法 要点
POST /auth/code
POST /auth/verify		 —（前端待补） 验证码 60s 冷却、单 IP 限流。verify 返回 access + refresh
GET /books shelfApi.listBooks 书架卡片。words / chapters / codexCount / guardOpen 全是聚合数，走物化视图或缓存，别每次现算
GET /projects/:id getProject 含卷列表、日更目标、绑定的风格档 id
GET /projects/:id/chapters listChapters 响应绝不含正文。80 万字作品（约 270 章）这个响应应在 100KB 以内
GET /chapters/:id getChapter 带正文。rev 必须返回，前端离线冲突判定要用
PUT /chapters/:id/body saveChapter 请求带 base_rev。若服务端 rev 更高返回 409 + 双方内容，前端并列展示。永不静默覆盖。保存成功后异步触发守卫扫描与 codex_refs 重建
PATCH /chapters/:id
POST /chapters/reorder		 —（前端待补 dnd） 元数据改动与拖拽换序分开。换序传 {id, before_id, after_id}，服务端算稀疏 idx
GET /projects/:id/codex
POST/PATCH/DELETE /codex/:id		 listCodex / confirmCodexEntry / dropCodexEntry 改名只改 name，正文无需迁移——引用存 id。改名后要重算该条目的 embedding
POST /generate/chapter streamChapter SSE。推 data: {"text":"…"} / data: {"node":2} / data: [DONE]，前端解析已写好。首帧前先推一条 {"layers":{…}} 让右栏显示实际装配情况。客户端断开必须真正中止上游请求，否则积分照扣
POST /generate/inline —（前端占位待接） 续写/扩写/润色/改写四个 action。传选区文本 + 前后各 500 字 + 本章引用条目。同样走 SSE，结果同样落 aiDraft
POST /generate/wizard/:step —（前端待接） 开书向导四步。每步结果落库，中途退出可续做——「< 5 分钟拿到第一章」的验收要求这个
GET /chapters/:id/context getContextLayers 四层预算预览，不真正调模型。右栏「已装配 21.4k token」读它
GET /projects/:id/guard
POST /guard/:id/resolve		 listGuardIssues / resolveGuardIssue 处置传 {resolution: 'keep-old' | 'keep-new' | 'intentional' | 'false-positive'}。前三种回写设定库，第四种回流评测集
GET /style/profiles
POST /style/upload
GET /style/:id/dimensions		 styleApi.list / dimensions 上传走对象存储直传 + 回调，5 万字文件别过应用层。抽取异步，前端轮询状态
GET /chapters/:id/ratio ratioApi.report 段落来源标记在采纳时已写入 content_json，此接口只做聚合 + 疑似句式匹配
POST /export
GET /export/:taskId		 —（前端待接） 异步打包，完成后给对象存储预签名 URL。不校验积分——导出免费是写进定价页的承诺
GET /usage shelfApi.usage / dailySeries 按 feature 聚合 usage_logs。基础档显示「免费」而非 0
SSE 的两个必须做对的细节：其一，Nginx 必须 proxy_buffering off 且 X-Accel-Buffering: no，否则首字延迟卡在缓冲区里，< 3s 的验收标准必然失败。其二，客户端 AbortController 断开时，FastAPI 侧要通过 await request.is_disconnected() 感知并真正中止上游模型请求——只停转发不停上游，用户按了「停止」但积分照扣完。

06  两条关键链路

生成链路决定成本与体验，守卫链路决定护城河。其余接口都是 CRUD，不值得单独画。

链路 A · 一键成章
前端 insertAiDraft()                      草稿容器就位，status=streaming
  │
  ├─ POST /generate/chapter { chapterId, targetWords, model, useStyleProfile, dialogueDensity }
  │
  ▼
services/generation.py
  1  quota.check()                        额度不足直接 402 + 降档建议，不静默失败
  2  memory.assembler.build()             ★ 四层装配
       layer1  稳定设定      ~6k   全量，序列化顺序固定 → 命中 prompt cache
       layer2  检索条目      ~5k   章纲实体抽取 → codex_aliases 精确命中 → pgvector 兜底
       layer3  前情摘要      ~4k   本卷已有章摘要 + 更早的卷摘要
       layer4  相邻原文     ~10k   前 2 章，从章末往前截
       budget.enforce()               超 25k 时按 layer4→3→2 顺序削，layer1 永不削
  3  gateway.router.pick()                任务=chapter → 主力档；model=advanced → 顶级档
  4  首帧先推 {"layers": {...}}            右栏立刻显示实际装配，不等正文
  5  流式转发，每段边界推 {"node": n}       章纲节点进度
  6  accounting.record()                  prompt/cached/completion token 分别记账
  │
  ▼
前端 appendDraftText() 逐帧写入          addToHistory: false，不污染撤销栈
  │
  ├─ 用户点「采纳」→ acceptDraftAt()      一次事务，段落打标 ai-raw
  │                  └→ PATCH /runs/:id/accepted  回写 accepted_words（北极星指标）
  └─ 用户点「停止」→ AbortController      服务端 is_disconnected() → 中止上游 → 按已生成量扣费
「重生成但保留锁定段」怎么实现：前端把 status='locked' 的草稿段落原文一并发给后端，作为 prompt 里的「已确定内容，请衔接而非重写」约束段。这段文本计入 layer4 预算。rejectAllDrafts 已经跳过 locked 节点，前端这块逻辑是现成的。
链路 B · 一致性守卫（MVP 成败点）
PUT /chapters/:id/body 成功
  │
  ├─ 同步：从 content_json 扫 CodexRef 节点 → 全量重建 codex_refs
  │        （同步做，因为下一次生成的 layer2 依赖它）
  │
  └─ 异步投递 Celery: guard_scan(chapter_id)      绝不阻塞写作
       │
       1  extractor.py    抽取本章新出现的实体与属性
       │                  → 新条目写 codex_entries(status='pending')
       │                  → 已有条目的新属性写入 attrs 的候选区
       │
       2  conflict.py     ★ 两阶段，成本与准确率的平衡
       │     阶段一  规则前置：attrs 的结构化字段做直接比对
       │              （左手=已断 vs 本章「左手接剑」→ 命中）
       │              规则能覆盖的部分零模型成本、零误报
       │     阶段二  LLM 判定：规则命中的候选 + 语义存疑的段落
       │              送中档模型做结构化输出 {is_conflict, reason, anchor}
       │              只判定候选，不全文扫描——这是成本可控的关键
       │
       3  foreshadow.py   伏笔登记与倒计时；超过 expected_by 未回收 → 升级 severity
       │
       4  anchor.py       为每条 issue 计算 {pid, start, end}
       │
       ▼
     guard_issues 落库 → 前端轮询或 SSE 推送 → 右栏红点

评测闭环：false_positive 标记 → guard/eval/ 数据集 → CI 跑召回率
目标：植入 20 处矛盾召回 ≥ 14，误报率 ≤ 20%
先做 spike，再对外承诺

召回 ≥ 14 / 20 这个数字是需求文档里的待决议项。第 1 周就要开始算法预研：手工构造 20 处矛盾的测试稿，先只用规则前置跑一遍，看规则能覆盖多少。规则覆盖率决定了整条链路的成本模型，也决定这个指标现不现实。

07  前端剩余工作

骨架已经能跑通全部 12 屏，剩下的活分三类：接后端、补性能、补缺失交互。按优先级排。

优先级 工作项 要做什么
必做 替换 mock 层 VITE_USE_MOCK=false，打开 vite proxy，把 mock/index.ts 每个方法换成 request()。签名一个都不改，视图层零改动。这是 README 已经写明的路径。
必做 保存改为带 rev 的乐观锁 use-autosave.ts 现在只发 html。要改成带 base_rev，收到 409 时把服务端版本和本地版本并列展示，让用户选。当前完全没有冲突处理。
必做 段落锚点 data-pid Paragraph 扩展加 pid 属性（nanoid，复制时重新生成）。守卫的「跳到出问题的那一句」靠它定位。越早做越便宜，有稿子之后再补要写迁移。
必做 离线队列换 Dexie 现在是 idb-keyval，单键读写。需要按章排队、失败重试、恢复时批量回放，键值对撑不住。HANDOFF 里写的就是 Dexie。
必做 章节树虚拟滚动 80 万字作品约 270 章，全量渲染 DOM 会拖垮首屏。@vueuse/core 的 useVirtualList 够用，不必上 tanstack。切章 < 200ms 的验收标准依赖这个。
必做 多作品切换打通 shelfApi 目前和 projectStore 没有连线。切书要清 project / codex / guard 三个 store，并处理 keep-alive 缓存失效。
该做 行内 AI 四个动作接真 runInline() 现在只插占位文本。改成走 POST /generate/inline，同样落进 aiDraft 节点，复用采纳/拒绝的现成交互。
该做 额度耗尽的降级引导 402 不能只弹「额度不足」。要给出「换标准模型继续」或「本章缩短到 2000 字」的具体下一步，否则用户卡在这里就走了。
该做 @引用改名跟随的视图刷新 条目存 id，所以改名后引用节点要重取显示名。改名接口返回受影响的 chapter_ids，前端只失效这些章的缓存。
可延后 移动端只读 非目标里排除了「移动端完整编辑」，但只读查阅设定库和已写章节，成本很低、留存收益明确。放二阶段。
一条不要碰的红线：不要为了「实时协作」提前引入 Yjs。chapter_bodies 已经独立成表、带 rev，将来换 CRDT 只动这一张表和一个接口。现在引入等于给 MVP 加一个分布式状态难题，而多人实时协作明确在非目标里。工作室产线要的是章节级分工不冲突，靠 chapter_assignments 加乐观锁就够，不需要字符级合并。

08  分阶段排期

基准 6 人 · 2 前端 / 2 后端 / 1 算法 / 1 设计。第一阶段 10 周对齐需求文档的里程碑，第二阶段 8 周做工作室产线。小团队降级路径见本节末。

第一阶段 · MVP 10 周
周次 里程碑 后端 前端 算法

第 7-8 周是唯一不能延的两周。其余功能延一周都只是体验打折，守卫做不到验收线，产品就退化成又一个「一键成章」工具——那个市场已经很挤了。所以第 1 周的 spike 必须出结论：如果规则前置只能覆盖三成，就要在第 3 周而不是第 8 周重新谈这个指标。
第二阶段 · 工作室产线 第 11-18 周

MVP 只建表不开功能：orgs / org_members / chapter_assignments 三张表随第一阶段一起上，projects.org_id 从第一天就写入。这样第二阶段不需要数据迁移，只需要把权限判断从「作者本人」放宽到「组织成员 + 角色」。

周次 交付 内容
11-12 席位与权限 组织创建、成员邀请、四种角色（owner / lead / writer / editor）；所有既有接口接入组织级鉴权；席位计费
13-14 章节分派与看板 chapter_assignments 开放；分派 / 认领 / 交回；进度看板；章节级软锁（同一章第二人进入时提示，不做字符级合并）
15-16 审校流 editor 角色的批注与打回；改稿留痕；5 人并行不冲突的验收演练
17-18 风格指纹 + AI 占比 ★ 作者风格指纹（≥5 万字样本，盲测「像我写的」≥60%）；AI 占比自查（采纳时打标，非事后检测）；拆书

风格指纹排在这里而不是更早，是因为它依赖 ≥5 万字 的真实样本。MVP 上线后才会有足够语料，提前做只能拿公开文本调，调出来的东西不解决「像我写的」。

09  风险与待决议

前四条是真实风险，各自带了退路。后三条是这份规划管不了、需要拍板的事。

风险 01 · 高

守卫达不到召回 14/20。这是唯一会让产品失去差异化的风险。

退路：把「自动召回」降级为「可疑标注」——不判定对错，只把涉及同一实体属性的前后文并列给用户看，由人判断。价值降低但仍强于市面产品，且误报率问题自动消失。第 3 周就要决定走不走这条。

风险 02 · 中

生成成本超出订阅定价。25k 输入 × 每章一次重生成 × 日更两章，单用户月成本可能吃掉 69 元里的大头。

退路：prompt caching 是主要手段，layer1 的 6k 命中缓存能省七八成输入成本——前提是序列化字节稳定。第 5 周装配器一上线就要看 generation_runs.layer_report 里的真实缓存命中率，不要等到有付费用户才算账。

风险 03 · 中

单文档编辑器在长章上仍然卡。一章一文档已经解决了 80 万字的问题，但个别作者会写单章 2 万字。

退路：TipTap 在 2 万字量级尚可，超过就在保存时提示拆章。这是内容规范问题，不值得为它上分块渲染。第 9 周压测时用 2 万字样本验一次。

风险 04 · 低

模型供应商变更或限流。

退路：自建薄网关的全部理由就在这里。路由表和回退链是配置而非代码，换供应商改一处。代价是要自己维护三家的 SSE 帧格式差异，约 300 行。

待决议 需要谁拍板 · 什么时候
守卫召回指标 产品 + 算法，第 3 周。spike 出数据后立刻定，不要拖到第 8 周才发现做不到。指标本身是需求文档里就标着待决议的。
免费额度与订阅档位 业务侧，第 6 周前。装配器一上线就有真实 token 成本，那时算比现在准。导出免费全量已经是定了的承诺，接口不校验积分。
风格指纹的语料授权 法务 + 产品，第二阶段启动前。用户上传自己的 5 万字来抽指纹，这份语料存多久、能不能用于模型侧优化，要写进条款。
下一步

后端从 memory/ 开始，不从 api/ 开始。四层上下文装配器是整个系统里唯一没有现成范式、且所有核心功能都依赖的部分——一键成章的质量、守卫的准确率、成本模型，全部由它的输出决定。CRUD 接口任何时候都能补，装配器越晚动手，越晚知道这个产品的成本和质量天花板在哪。
